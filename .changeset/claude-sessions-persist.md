claude sessions now persist, so a delegation's `sessionId` is genuinely resumable. `--no-session-persistence` makes the CLI print a session id that `claude --resume <id>` rejects with "No conversation found" (live-verified on 2.1.325), so a fresh claude run reported a resumable-looking id while every follow-up on it — `--resume=`, the tool's `sessionId`, a fan-out resume — failed at the CLI with a confusing error. The default is now to persist; `harnesses.claude.sessionPersistence: false` restores the old no-file behavior for anyone who does not want per-run session files under `~/.claude`, accepting that those runs then report `sessionId: null` (never an id nothing can load). What persisting costs, stated plainly: each run writes a Claude Code session file under `~/.claude/projects/<cwd-slug>/` holding the delegated prompt, tool I/O and any fenced diff; it is retained by Claude Code's own `cleanupPeriodDays` (30 by default), not this extension's `maxTranscripts`, it does not carry this extension's `0600` mode, and it shows up in your interactive `claude --resume` picker for that project. The field is dropped at load time unless it is a real boolean (never coerced), `--resume` always takes precedence over it, and no other harness changes.
