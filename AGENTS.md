# AGENTS.md

Guidance for AI coding agents working in this repository.

`pi-harness-delegate` is a [pi coding agent](https://github.com/badlogic/pi-mono) extension that delegates work to multiple harnesses (Claude Code, Muse, OpenCode, Amp, Devin) headlessly. It ships as an npm package (`pi-package` keyword), installable with `pi install npm:pi-harness-delegate`.

> `CLAUDE.md` is a symlink to `AGENTS.md` — keep them in sync.

## Commands

| Command | What it does |
| --- | --- |
| `bun run typecheck` | `tsc --noEmit` over `extensions/` (strict, `allowImportingTsExtensions`) |
| `bun test` | `bun test` (164 tests, bun:test — node:test compatible) |
| `bun run lint` | `biome check .` (2 spaces, 120 cols, single quotes) |
| `bun run lint:fix` | `biome check --write .` |
| `bun run verify` | `lint + typecheck + test` — CI and release both run this |
| `bun changeset` | Create a changeset `.md` (commit it); `--empty` for docs/CI-only |
| `bun run version-packages` | Changesets bump + CHANGELOG (run by release workflow) |
| `bun run release` | `typecheck + check-packables + changeset publish` (OIDC) |
| `pi -e <path> -p "…" --no-tools` | Load local package as temp extension; smoke-tests manifest + factory |

CI (`.github/workflows/ci.yml`) runs `verify` + `check-packables` + changeset presence on every push/PR. Release (`.github/workflows/release.yml`) is changesets + OIDC trusted publishing — no npm token.

## Architecture

- `extensions/index.ts` — entry. Registers `delegate` tool (primary) + `claude_delegate` alias, and `/delegate` command (primary) + `/claude`, `/codex`, `/opencode`, `/amp`, `/omp`, `/devin` aliases. Reads `delegate` config (with legacy `claudeDelegate` migration), builds prompts, writes partitioned transcripts, renders live feed. `delegate()` is the shared engine — single source of truth for one harness run; everything else (fan-out, verify) is built on top of it, never around it. Resolves the transport via `resolveTransport(config, harnessName, harness)` (config.ts) **before** `acquireSlot()`/spawn — config override, falling back to the harness's own default, validated against `harness.supportsTransports` so an unsupported value (e.g. `transport: 'acp'` for `claude`) fails immediately with a clear message instead of a cryptic spawn error — then selects the runner at the one call site inside `delegate()` (`runHarness` for `'stdout'`, `runAcpHarness({...opts, harness: acpView(harness)})` for `'acp'` — `acpView`, in `acp-runner.ts`, presents the ACP-shaped fields of a dual-transport harness). The stdout call is byte-identical to before per-harness transport existed.
  - **Verify**: after `delegate()` gets a result back from the harness (success or error-with-output), it resolves a verify command via `resolveVerifyPlan(opts.verify, template.verify, permission)` (activity.ts, pure — per-call override wins over the template's) and, if one is configured, either runs it host-side via `runVerify()` (`pi.exec('sh', ['-c', command], {cwd, timeout: VERIFY_TIMEOUT_MS})` — never delegated to the harness) or records it as skipped via `skipVerifyResult()`. **Trust model** (see the comment on `runVerify` in `index.ts`): a verify command has exactly two legitimate sources — on-disk template frontmatter (project-local templates already behind `isTrusted()`) or a human typing `/delegate --verify=<cmd>`. It is **not** a `delegate` tool parameter — `DelegateToolParams` deliberately omits it, because a tool param is model-settable and the model's context (repo content, delegated-harness output) is attacker-influenceable, making a model-settable `verify` a prompt-injection → arbitrary-host-command path. `resolveVerifyPlan` also never lets a configured command actually run when `permission === 'readonly'` — a `readonly` run's whole guarantee is "no execution/modification," so a verify command riding along on one would be a permission-tier bypass regardless of how trusted its source is; the skip is recorded (`### Verify: \`cmd\`` / `⊘ skipped (readonly run)`), never silently dropped. The `VerifyResult` is otherwise report-only: appended as its own section in the transcript (`buildTranscript`) and injected report (`buildReportContent`), and surfaced whole in the tool result's `details.verify` — it never touches `result.isError`. Skipped entirely (no section at all) when no command is configured (no invented default).
  - **Fan-out** (`harness: "all"` or a comma list, e.g. `"claude,codex"`): detected via `isFanoutSpec()` (command.ts). `resolveHarnessList()` (command.ts, pure) resolves the spec against `detectAll()` — `all` → every *detected* harness, an explicit list is alias/known-validated and also detection-filtered — uninstalled/unknown names are reported (`skipped`/`unknown`) rather than failing the run. The tool path (`runFanoutTool`) and the `/delegate` command path (`runFanoutCommand` → `runFanoutConcurrent`) both launch `delegate()` **concurrently, once per resolved harness**, all at once (`specs.map(...)` + `Promise.all`, not a sequential loop) — every call passes `waitForSlot: true`, so `acquireSlot` (concurrency.ts) is what actually bounds how many run at a time: it queues a run that doesn't fit under `maxConcurrent` instead of failing it, so a fan-out never exceeds the cap just because it launched everything at once. Each run writes its own transcript via the existing per-harness `outputsDir`. Results are collected (out of completion order) and reordered via `orderFanoutResults()` (activity.ts, pure) back to the resolved harness list before being mechanically assembled — no second model call — into one comparison report via `buildFanoutReport()` (activity.ts), which reuses `aggregateSpend`/`formatSpend` for the total-spend rollup; this keeps the report deterministic regardless of which harness actually finishes first. A single-harness call is untouched by any of this (still `waitForSlot: false`, fails fast) — fan-out is purely additive, gated on `isFanoutSpec`.
  - **Notifications**: `/delegate all …` batches successful per-harness completions through `NotifyBatcher` (`extensions/notify.ts`) so the fan-out emits one debounced notification instead of one per harness; failures call `.failure()`, which flushes any pending batch and emits immediately — never delayed or batched. Since runs are concurrent, notifications now land in completion order, not resolved-harness order (only the synthesized report is order-normalized). Confined to the command handler's `ctx.ui.notify` path, guarded by `ctx.hasUI`; not a general event system.
- `extensions/harnesses/types.ts` — normalized `NormalizedPermission = readonly|edit|danger`, `StreamedResult` (`numTurns`/`totalCostUsd` are `number | null` — `null` means the harness's payload didn't report the field, not a measured 0), `ActivityEvent` (`tool_input`/`tool_result` carry an optional `id` used to attribute a result to its originating call in a parallel batch), `ParseState`, `BuildArgsOpts`, `Transport = 'stdout' | 'acp'` (default `'stdout'` when a harness omits it — only `devin` sets `'acp'`), `DEFAULT_TIMEOUT_MS`. `Harness` interface: `name`, `binary`, `detect()`, `buildArgs()`/`parseLine()`/`permissionMap` (stdout transport), optional `buildAcpArgs()`/`parseAcpLine()`/`acpPermissionMap` (ACP transport — each falls back to its stdout-shaped counterpart when absent, so an ACP-only harness like Devin doesn't need to declare them twice), `extractResult()` (shared across both transports), `transport` (this harness's *default*), `supportsTransports?: Transport[]` (the *ceiling* `resolveTransport` validates config against — independent of the default; omitted means `[transport ?? 'stdout']`). `permissionMap` and `acpPermissionMap` are deliberately separate fields even when a harness's values happen to coincide (opencode) — they're different vocabularies (CLI arg fragments vs. ACP `session/set_mode` mode ids) that only look the same by day-one coincidence.
- `extensions/harnesses/claude.ts` — Claude Code runner: `claude -p --output-format stream-json --verbose` (+ `--no-session-persistence`/`--resume`), maps `readonly→plan`, `edit→acceptEdits`, `danger→bypassPermissions`. Wires `tool_use.id`/`tool_result.tool_use_id` into `ActivityEvent.id`. Schema verified against Claude Code 2.1.247.
- `extensions/harnesses/codex.ts` — Muse: `codex exec --json` + `--sandbox read-only|workspace-write|danger-full-access` (resume is the `codex exec resume <id> <prompt>` subcommand, not a flag — codex-cli dropped `--ask-for-approval` and `--thread-id` from `exec` entirely; `exec` is non-interactive by design so sandbox alone governs approval). Wires `item.id` (shared by `item.started`/`item.completed`) into `ActivityEvent.id`; `item.type` (e.g. `command_execution`) doubles as the tool name since items don't carry a `name` field. `turn.completed.usage` (`input_tokens`/`cached_input_tokens`/`cache_write_input_tokens`/`output_tokens`) is the real final-usage event — this codex-cli version never reports a `$` cost (ChatGPT-plan auth), so `totalCostUsd` stays `null`; `numTurns` is a genuine count of `turn.started` events, not a field the payload reports. Schema verified against codex-cli 0.149.1 — see `tests/fixtures/codex.jsonl`.
- `extensions/harnesses/opencode.ts` — OpenCode, the one **dual-transport** harness so far (`supportsTransports: ['stdout', 'acp']`, defaults to `'stdout'`). Stdout: `opencode run <prompt> --format json --agent plan|build[ --auto]` (this CLI version has no `--permission` or `--add-dir` flag at all — permission tiers map onto opencode's built-in agents instead: `plan` read-only, `build` full-access, `--auto` for danger-tier auto-approval; `addDirs` is silently unsupported). Wires `part.callID` into `ActivityEvent.id` — each tool call arrives as one already-resolved `tool_use` event (no separate pending/start line), so `tool_input`+`tool_result` are synthesized together from it. `step_finish.part.cost`/`.tokens` report *per-step* deltas, not a running total, so `totalCostUsd`/`usage`/`numTurns` are accumulated across every `step_finish` seen in the stream. Schema verified against opencode 1.18.16 — see `tests/fixtures/opencode.jsonl`.
  - **ACP** (`buildAcpArgs` → `['acp']`, no `--model` — `opencode acp --help` has no such flag): `parseOpencodeAcpLine` translates the same `session/update` dialect as `devin.ts` (real, live-verified: opencode's compiled binary shares an ACP implementation with omp — see `docs/acp-harness-assessment.md` §2), kept as an independent function rather than a shared import so `devin.ts` needs zero changes. Genuine gains over stdout: real `contextWindow`/`cost` (latched from the *last* `usage_update` seen — server-side running total per session, not summed like `step_finish` — `usage_update.cost.amount`/`.size`), and a `sessionId`/`session/load` resume path independently proven to recall cross-process state (`tests/fixtures/opencode-acp.jsonl`, including a same-process `session/load` replay). `model`/`numTurns` stay `null` — never confirmed back over ACP, unlike Devin's `agent_stopped` event. **The one thing this needed a live run to close**: does opencode's `build` mode (where `edit`/`danger` both land) ever call `session/request_permission` for a write — which `acp-runner.ts`'s defensive client auto-declines? A second live run answered no — a real write prompt under `build` produced a `tool_call`/`tool_call_update` with `kind: "edit"` and no permission request at all (`tests/fixtures/opencode-acp-build-write.jsonl`), so `edit`/`danger` genuinely execute over ACP. `acpPermissionMap` (`plan`/`build`/`build`) is a separate field from `permissionMap` even though the values coincide today — see the types.ts bullet.
- `extensions/harnesses/amp.ts` — Amp/Omp: `<binary> -p --mode json --approval-mode always-ask|write|yolo`, alias `omp→amp`. **`omp` here is "Oh My Pi", a `pi`-framework-based CLI — not a drop-in rebrand of Sourcegraph's Amp** (confirmed via `omp --help`: entirely different flag surface, e.g. `--mode`/`--approval-mode` vs. the real Amp CLI's assumed `--output`/`--permission`). It's simply the only binary of this harness installed on the capture machine, and its JSONL envelope (`session`/`turn_end`/`agent_end`/…) is what got captured and wired; behavior against the real Sourcegraph `amp` CLI is unverified. `binary` resolves to whichever of `amp`/`omp` actually exists on `PATH` at module load (`resolveAmpBinary`) — previously it was hardcoded to `'amp'`, so a machine with only `omp` installed could never actually spawn this harness despite `detect()` reporting it as available. Wires `toolCallId` into `ActivityEvent.id`. `message.usage.cost.total`/`.input`/`.output` on `turn_end` are per-turn, not cumulative (confirmed: three real turns each reported similar-magnitude token counts, not compounding ones) — accumulated across every `turn_end` for a genuine session total; `agent_end` reads the same accumulator rather than re-deriving from `o.message` (which doesn't exist on `agent_end` — it's `o.messages`, an array — a bug that silently nulled out the final result before this fix). Schema verified against omp 17.2.9 — see `tests/fixtures/amp.jsonl`. `supportsTransports: ['stdout']` only — `omp acp` is real and live-verified, but its ACP mode surface has only 2 tiers (`default`/`plan`) against the stdout `--approval-mode`'s genuine 3 (`always-ask`/`write`/`yolo`); offering `transport: 'acp'` at all would let a user silently lose the `edit` tier's distinct semantics, so it's not a legal config value (`docs/acp-harness-assessment.md` §5).
- `extensions/harnesses/devin.ts` — Devin over the Agent Client Protocol (`devin acp`), not stdout JSONL: `transport: 'acp'`, `buildArgs` returns `['acp']` plus `['--model', opts.model]` when a model is resolved (prompt/permission/session lifecycle are otherwise all negotiated over the wire by `acp-runner.ts`, not CLI flags). Maps `readonly→plan`, `edit→accept-edits`, `danger→bypass` (exact structural match to Claude's tiers; `ask`/`smart` stay reachable via `nativePermission`). `parseLine`/`extractResult` translate raw ACP JSON-RPC lines — each one is a JSONL line like any other harness's — into `ParseOutcome`/`StreamedResult`: `session/update` → `tool_call`/`tool_call_update` wire the real `toolCallId` into `ActivityEvent.id` (only a terminal `completed`/`failed` status produces a `tool_result` — a call fires 2-3 `in_progress` updates first, and `ToolCallIndex.resolve()` would consume the pending entry on the first one), `agent_message_chunk`/`agent_thought_chunk` → streamedText/`thinking`, `usage_update` → `contextWindow`, `_cognition.ai/agent_stopped`'s `stats.modelLabel` → `model` (the model Devin actually ran, read back rather than echoed from the request — `--model` takes fuzzy names and can be fuzzy-matched or enterprise-overridden). `usage.inputTokens` is `devinInputTokens - devinCachedReadTokens` (floored at 0) — Devin's own `inputTokens` already includes cached-read tokens as a subset (fixture: `used === inputTokens + outputTokens` exactly), but `StreamedUsage.inputTokens` must exclude them (Claude's convention; `index.ts` adds `cacheReadInputTokens` back in for `promptTokens`), or context-window % is inflated ~2x. `totalCostUsd`/`numTurns` stay `null` — Devin reports neither over ACP (honest-metrics convention, #11). Schema verified against `devin 3000.6.7 (260a97c8)` — see `tests/fixtures/devin-acp.jsonl` and `docs/devin-acp-harness-design.md`. `supportsTransports: ['acp']` — no stdout mode exists to select between, so there's nothing to configure. **Workspace trust does not gate `devin acp`** (only `devin -p`/interactive `devin`) — confirmed live against a directory devin had never seen, so `detect()` doesn't carry a trust hint and this harness never touches Devin's `skip_workspace_trust` config key.
- `extensions/harnesses/registry.ts` — `HARNESSES`, `ALIASES`, `getHarness()`, `detectAll()`, `isKnownHarness()`.
- `extensions/runner.ts` — generic `runHarness(harness, opts)` spawn+readline loop calling `harness.parseLine`/`extractResult`, handles timeout, AbortSignal, TTFT. Used for every harness whose `transport` is `'stdout'`/omitted (claude, codex, opencode, amp).
- `extensions/acp-runner.ts` — sibling to `runner.ts` for the `'acp'` transport (devin, always; opencode, when configured). ACP (https://agentclientprotocol.com) is JSON-RPC 2.0 over stdio, bidirectional and stateful, unlike the stdout harnesses' one-way JSONL stream — `runAcpHarness(opts)` exposes the exact same `RunHarnessOptions`/`HarnessResult` shape as `runHarness` so `delegate()` and everything downstream (transcripts, `ToolCallIndex`, overlays, fan-out, spend) is unchanged. `acpView(harness)` (exported) presents the ACP-shaped fields of a dual-transport `Harness` (`buildAcpArgs`→`buildArgs`, `parseAcpLine`→`parseLine`, `acpPermissionMap`→`permissionMap`) to this file, falling back to the stdout-shaped names for an ACP-only harness like Devin — this file itself always reads the stdout-shaped field names and needed zero changes for that split. Drives the handshake (`initialize` → `session/new` or `session/load` when `opts.resumeSessionId` is set → `session/set_mode` → `session/prompt`). `initialize`'s negotiated `protocolVersion` is checked against what was sent and fails clearly on a mismatch (only `1` has ever shipped, so this is currently inert insurance, not observed behavior). `session/set_mode` is capability-checked first via `supportsSessionModes()` — true if `session/new`/`session/load`'s response has the spec-standard `modes` field (Devin, omp) **or** a `configOptions` entry with `category: "mode"` (opencode, which never populates `modes` but implements `session/set_mode` anyway; omp has both) — and if neither signal is present, the run fails immediately with a clear message rather than either calling a method the agent may not implement or silently running at the agent's default (unconfirmed) permissiveness; every real agent captured so far advertises one of the two signals, so this never fires today. Holds `stdin` open for the run (`stdio: ['pipe','pipe','pipe']` — the existing stdout harnesses use `'ignore'`; ACP agents exit on stdin EOF), and mirrors `runner.ts`'s 5MB `streamedText` cap / 5000-activity cap and timeout/AbortSignal-kill behavior. Every incoming line is fed through `harness.parseLine` (same as `runner.ts`) in addition to the runner's own request/response correlation (a `Map<id, PendingRequest>`, each handshake step bounded by `HANDSHAKE_TIMEOUT_MS` separate from the overall `timeoutMs` so a hung handshake fails fast instead of wedging the whole budget). Two gotchas found only by running it, not reading the spec: (1) the agent does **not** exit once `session/prompt` resolves — an ACP session can outlive one turn (resume, follow-up prompts) — so the runner explicitly `finish()`es off `state.result` as soon as the response resolves and kills the process itself, rather than waiting for `proc.on('close')`, which could hang indefinitely; (2) `session/load`'s response carries no `sessionId` of its own (unlike `session/new`'s), so the runner stashes `opts.resumeSessionId` into `state._harness` itself so the harness's `parseLine` can still report it on the final result. Server-initiated requests (permission prompts, fs reads) get a defensive, always-answered response — `session/request_permission` picks a `reject_once`/`reject_always` option (or `cancelled` if none), everything else gets a JSON-RPC error — since we run non-interactively with a mode already negotiated; never observed in the captured fixture, but every request needs a reply or the agent hangs. **Every exit path kills the child process** — timeout, abort, success, and (as of the process-leak fix) a rejected handshake step too: the handshake IIFE's `.catch` now `proc.kill('SIGKILL')`s before `fail()`s, matching the other three paths; without it, ACP agents (stdin-EOF-only exit, never sent on this path) leaked indefinitely — confirmed live both ways with the same repro (`session/load` against a nonexistent `sessionId`, which devin genuinely rejects with a JSON-RPC error). **Resume discards replayed history**: `session/load` replays every prior turn as `session/update` notifications before the new prompt's; a `promptSent` flag (set only once `session/prompt` is actually sent) gates whether `parseLine`'s `streamedText`/`activities` output is forwarded to `state`/`onStream`/`onActivity`, so replayed content from a resume never reaches the caller — verified live: a fresh process resuming a session created by an earlier one returned only the new turn's answer, while still correctly recalling information only given in the first turn.
- `extensions/run-claude.ts` — deprecated wrapper around `runHarness(claudeHarness)` + `HarnessBuildOpts` compat.
- `extensions/stream-parse.ts` — deprecated wrapper around `parseClaudeLine`.
- `extensions/templates.ts` — template discovery + frontmatter (`permission: readonly|edit|danger` preferred, legacy `permissionMode`/`sandbox` as native escape hatch; `verify` — optional host-run check command, e.g. `bun test`). Load order: `shared < builtin < user-global < project-local`, later wins on name collision. Partitioned per harness plus legacy dirs. A project-local template's `verify` command is gated by the same `isTrusted()` check as the rest of the template (project dirs are only loaded when trusted) — an untrusted clone cannot smuggle in a verify command any more than it can override a template's prompt.
- `extensions/command.ts` — parser for `/delegate` + aliases: `--harness` (single name, `all`, or a comma list), `--mode`, `--model`, `--scope`, `--budget`, `--resume`, `--pr`, `--verify` (flag values may be quoted, `--verify="bun test"`, so multi-word commands survive), plus harness/mode as first words (`looksLikeHarnessSpec` recognizes `all` and comma lists as the harness word too). Also home to the fan-out helpers: `isFanoutSpec()` and the pure `resolveHarnessList()` (detection results passed in, no I/O).
- `extensions/config.ts` — `loadConfig()` reads `delegate` (and migrates legacy `claudeDelegate`), `agentDir()`, `outputsDir(harness)` partitioned (`~/.pi/agent/delegate/outputs/<harness>`), `resolveModelForHarness()`. `HarnessConfig.transport?: 'stdout' | 'acp'` — a malformed value is dropped at load time (same defensive-parsing style as every other per-harness field); a well-formed but unsupported one isn't dropped here, `resolveTransport(cfg, harnessName, harness)` validates it against `harness.supportsTransports` instead and throws a clear message, so misconfiguring it fails the run rather than being silently ignored.
- `extensions/run-registry.ts` — file-based active-run registry (`acquireRun`/`releaseRun`/`countActiveRuns`) under `<agentDir>/delegate/runs/`, one JSON file per active run, so the concurrency guard and `/delegate status` active count are accurate across pi processes, not just the current one. Best-effort (never throws); stale entries from dead pids *and* entries with a corrupt/non-numeric `pid` are cleaned up on read (`process.kill(pid, 0)`, treating `EPERM` as alive). `concurrency.ts` combines it with an in-process counter via `Math.max` as a fallback. **`maxConcurrent` is a best-effort cap, not a hard mutex** — `countActiveRuns()` (read) and `acquireRun()` (write) are separate, unlocked steps, so two pi processes starting at the same instant can both observe a count under the limit and both proceed.
- `extensions/concurrency.ts` — the `delegate()` concurrency guard, factored out so it's testable without the TUI or an `ExtensionAPI`. `acquireSlot({harness, mode, config, wait, signal})` is the single choke point: checks the global limit then the per-harness limit (same precedence/error text as before the refactor), and either throws `ConcurrencyLimitError` immediately (`wait: false` — unchanged single-run fail-fast UX) or polls every `pollIntervalMs` (default 200ms) until a slot frees (`wait: true` — what fan-out uses; this *is* the bounded pool, there's no separate worker-pool structure). Resolves with an idempotent release function. `activeCount(harness?)`/`inProcessActiveCount(harness?)` expose the counters for `/delegate status`.
- `extensions/activity.ts` — formatters (`formatToolUse`), `ToolCallIndex` (matches a `tool_result` to its originating `tool_input` by id, falling back to "last entry" when no id — shared by the transcript log and the live-feed builders), `collectActivityLog`, `buildTranscript(harness, permission, nativePermission)`, `parseTranscriptMeta` (now returns harness; `cost` is `number | null`), `buildReportContent(harness,mode)`, `aggregateSpend`/`formatSpend` (pure cost/run-count rollup used by `/delegate status`), `pruneOutputs`. Also: `VerifyResult` + `resolveVerifyCommand`/`buildVerifyResult`/`formatVerifySection` (verify command resolution and report rendering — both `buildTranscript` and `buildReportContent` take an optional `verify` and append its section), and `FanoutRunSummary` + `buildFanoutReport` (mechanical, header-free comparison-report body for a fan-out — callers wrap it with their own `## <label> (...)` header).
- `extensions/notify.ts` — `NotifyBatcher`: batches successful fan-out completions into one debounced notification; `.failure()` flushes the pending batch and emits immediately, never delayed. Used only by the `/delegate all …` command path.
- `extensions/progress.ts` — single-run progress-window overlay (spinner, double-ESC cancel, `m` minimize, `danger` banner). `FeedEntry`'s `tool` variant carries an optional `id` for the same result-attribution matching. Used by `runOneDelegation` for every single-harness `/delegate` run — unchanged by the fan-out work. `truncateFeed()` (pure) slices the feed to `MAX_VISIBLE_ENTRIES` and reports how many were dropped, so the overlay renders a dim `+N earlier` marker instead of truncating silently.
- `extensions/progress-multi.ts` — the fan-out counterpart: one overlay showing every concurrent run as a compact row (`RunRow`: harness, `queued|running|done|failed` status, elapsed since it acquired its slot, current activity text, `costUsd` once it completes) instead of N stacked overlays or one feed with interleaved lines from different harnesses. `multiProgressWindow()` has the same double-ESC-cancel/`m`-minimize controls as `progressWindow`; deliberately a sibling module, not merged into `progress.ts` or a generic layout framework — the two render fundamentally different things. `renderRowLabel()` (marker + harness name) and `formatFanoutChip(rows, elapsedMs)` (status-bar summary — per-status counts with zero counts omitted, plus `⏱ <elapsed>` and aggregate `$<spend>` once at least one run has reported a cost) are exported pure for testing; `elapsedMs` is passed in rather than read from `Date.now()` internally so the function stays pure. A failed row keeps the failure reason (or its last activity) as its activity text instead of blanking — the moment a row goes red is exactly when its context matters. `isFanoutComplete(rows)` (pure) is true once every row is terminal; `multiProgressWindow` uses it to switch Esc/`m` from "arm cancel"/"minimize" to an immediate dismiss once there's nothing left to cancel, which `runFanoutConcurrent` (`index.ts`) pairs with a `FANOUT_LINGER_MS` (~3s) post-completion linger before it tears the overlay down on its own — run detached after `runFanoutConcurrent` returns its outcomes, so the linger never delays the caller or the injected report; an explicit cancel skips the linger since it already signals "done watching."
- Subcommand UIs in `index.ts`: `/delegate list [harness]`, `/delegate history` (partitioned, with scrollable viewer + resume, legacy dir filtered for `-partial` transcripts same as the partitioned dirs), and `/delegate status` (per-harness spend rollup via `aggregateSpend`, e.g. `$1.234 over 12 run(s) (3 unknown)` — unknown-cost runs are never folded into the total silently).
- Config surface: `modelAliases` (`economy/balanced/max`), `maxConcurrent` (global + per-harness, default `4` — genuinely parallel now, not just "don't overlap": see the Fan-out bullet above), `maxTranscripts` (`pruneOutputs` per harness).
- `extensions/usage.ts` — maps harness usage/cost to pi `Usage` (cacheCreation folds into input). `mapHarnessUsage`/`mapClaudeUsage` return `undefined` when cost is unknown rather than reporting a fake $0 into pi's session totals — callers must handle the `Usage | undefined` result.

## Conventions

- **2 spaces**, single quotes, 120-col lines — enforced by Biome (`biome.json`: 2 spaces, 120, singleQuote, trailing all). Run `bun run lint:fix` if a diff looks unformatted.
- TypeScript strict; explicit types on exported functions.
- Relative imports **must include `.ts`** (`./runner.ts`) — jiti + `allowImportingTsExtensions`.
- **Templates live as .md files with frontmatter**, never as code strings. Frontmatter: `name, description, permission: readonly|edit|danger, model, maxBudgetUsd, skill, defaultTask, defaultScope`. Legacy `permissionMode`/`sandbox` preserved as native escape hatch.
- **Never default to `danger`.** Only path is explicit `allowDangerous:true` on a call. `review`/`plan`/`security-audit` stay `readonly`.
- Guard UI calls (`ctx.ui.*`) with `ctx.hasUI` — tools run in all modes.
- Scope `diff`/`pr` resolved in-process via `git diff HEAD` / `gh pr diff`; don't rely on harness running git.
- **Unmeasured metrics are `null`, never a fake `0`.** `numTurns`/`totalCostUsd` on `StreamedResult` and `cost` on `parseTranscriptMeta` are `number | null` — `null` means the harness's payload didn't report the field. Render `null` as `—`/`n/a` (`formatMetrics`, `buildTranscript`, `/delegate status`, `/delegate history`), never `0`/`$0.000` — a real `$0` run and an unmeasured run must stay visually distinct.
- **Verify is report-only, trusted-source-only, and never on `readonly`.** A `verify` command (frontmatter `verify:` or the `/delegate --verify=` flag) runs host-side after the harness exits and its pass/fail is recorded alongside the result — it must never flip `isError`, which stays exactly what the harness itself reported. Never invent a default verify command for a template. **`verify` is not, and must never become, a `delegate` tool parameter** — a tool param is model-settable, and the model's context (repo content, delegated-harness output) is attacker-influenceable, so that would be a prompt-injection → arbitrary-host-command path; the only legitimate sources are on-disk template frontmatter and direct human input. A verify command must also never actually execute on a `permission: readonly` run — that would silently break `readonly`'s no-execution guarantee — so `resolveVerifyPlan` always skips it there (recorded, not dropped) regardless of who configured it.
- **Fan-out never bypasses the concurrency guard — it queues through it instead of failing.** `harness: "all"`/a comma list launches `delegate()` concurrently for every resolved harness (`Promise.all`), each passing `waitForSlot: true` to `acquireSlot` (concurrency.ts) so a run beyond `maxConcurrent` waits for a slot instead of erroring out. A single-harness call must keep `waitForSlot` unset/`false` — it should still fail fast (`ConcurrencyLimitError`) at capacity, exactly as before this existed. Do not add a second, independent concurrency limiter (e.g. a fixed-size worker pool) alongside `acquireSlot` — it's already the one bounded-pool primitive; reuse it.

## Release process (changesets + OIDC)

Changesets + OIDC trusted publishing. No manual `version` bump, no `npm publish`.

1. Edit code → `bun run verify`.
2. `bun changeset` (or `bun changeset --empty` for docs/CI) → commit `.changeset/*.md`. **Important:** `package.json:files` includes `README.md` (and `templates/` for this repo), so even README/docs-only PRs are considered a package change — `ci: Changeset present` (`changeset status --since=origin/main`) will fail without a changeset. For docs-only that should not bump the version, run after `bun install`:
   ```bash
   bun install
   ./node_modules/.bin/changeset add --empty   # creates .changeset/*.md with ---/--- (no bump)
   git add .changeset/*.md && git commit
   ```
   This satisfies CI with `Packages to be bumped:` empty.
3. PR → CI checks `changeset status --since=origin/main`.
4. Merge to `main` → Release workflow opens/updates `chore: version packages` PR (bumps `package.json` + `CHANGELOG.md`).
5. Review version numbers → Merge Version Packages PR → Release workflow runs `bun run release` (`typecheck + check-packables + changeset publish`), creates tag `vX.Y.Z` pinned to `$GITHUB_SHA` + one GitHub Release, verifies `latest` dist-tag.
6. On machines with the package installed: `pi update --extensions`.

Load-test a local change: `pi -e <repo path> -p "Reply with exactly: OK" --no-tools`. Engine can be exercised without pi: `bun --input-type=module -e "import {runHarness} from './extensions/runner.ts'; import {claudeHarness} from './extensions/harnesses/claude.ts'; …"`.

Load-test the release guard: `node scripts/check-packables.mjs` — must pass; fails on `0.0.0` or empty `extensions/`.

## Gotchas (each cost real time — don't rediscover them)

- Unscoped `pi-harness-delegate` — no `--access public` dance for scoped name; but keep `files: ["extensions","templates"]` so subdirs ship.
- `stream-json` requires `--verbose` for claude (do not drop).
- `--no-session-persistence` keeps claude runs from littering session files; other harnesses use their own session flags.
- Peer deps `"*"` (`pi-ai`, `pi-coding-agent`, `pi-tui`, `typebox`) — pi bundles them; never add to `dependencies`.
- Harness CLIs change args often — version-gate `detect()` and snapshot one real JSONL transcript before locking parser. Confirmed the hard way: as of codex-cli 0.149.1 and opencode 1.18.16, the flags this repo previously assumed (`codex exec --ask-for-approval`, `codex exec --thread-id`, `opencode run --permission`, `opencode run --add-dir`) are all rejected outright by those CLIs — every codex/opencode delegation would fail before emitting a single JSONL line. Re-verify flags against `<binary> <subcommand> --help` whenever bumping a pinned harness version, not just the JSONL schema.
- `amp`/`omp` isn't one CLI with two names — `omp` ("Oh My Pi") has a completely different flag surface from the real Sourcegraph Amp CLI it's aliased to. Its `resolveAmpBinary()` PATH probe (in `amp.ts`) only picks whichever binary is actually present; it doesn't validate that binary's schema matches what's wired.
- **Bun for dev, npm for publish.** CI/release use `bun install`/`bun run` everywhere, but `bun run release` calls `changeset publish` which runs `npm publish --provenance` via npm (OIDC). No npm token in repo — `id-token: write` mints it. First publish of a new package must be local with 2FA (`bun run release`).
- `devin`'s interactive workspace-trust gate (`devin -p`/interactive `devin` refuse in an untrusted directory) does **not** apply to `devin acp` — confirmed live: the raw ACP `initialize`/`session/new` handshake against a directory `devin` had never seen succeeded with no refusal, in the same test where `devin -p` in that exact directory refused. Don't add a trust-check hint or a `skip_workspace_trust` bypass on the strength of the design note's `-p`-based finding without re-verifying against the actual `acp` subcommand — it's not the same gate.
- An ACP agent does not exit once `session/prompt`'s response arrives — the session can outlive one turn. `acp-runner.ts` must explicitly finish and kill the process itself the moment that response resolves; waiting on `proc.on('close')` (the stdout harnesses' pattern) hangs until the process's own timeout, because `stdin` is deliberately held open for the run.
- Every exit path in `acp-runner.ts` must `proc.kill()` — an ACP agent exits only on stdin EOF (never sent) and `fail()`/`finish()` don't kill on their own. A handshake-step rejection (bad modeId, JSON-RPC error, `HANDSHAKE_TIMEOUT_MS`) is easy to miss since it's the one path that doesn't already have a kill nearby — the `.catch` on the handshake IIFE needs its own explicit `proc.kill('SIGKILL')`, confirmed to leak a live `devin acp` process without it.
- `session/set_mode` is spec-optional (`Agent.setSessionMode` is `?`, `NewSessionResponse.modes` is nullable) — calling it unconditionally would fail the whole handshake with a raw "method not found" against a mode-less agent instead of a clear message. `acp-runner.ts` checks capability first (see the bullet above); a harness that can't confirm mode support is a hard error, not a silent downgrade to whatever permissiveness the agent defaults to — we already promised the caller a specific tier.
- opencode's `build` mode (where `edit`/`danger` both land over ACP) does **not** call `session/request_permission` for a write — live-verified with a real file-creation prompt (`tests/fixtures/opencode-acp-build-write.jsonl`). This was the one open question gating whether opencode ACP shipped at all (`docs/acp-harness-assessment.md` §4/§7) — closing it needed an actual write attempt under `build`, not just reasoning from the `plan`-mode block that was already captured.

## Scope notes

- Do not add a second delegation mechanism — harnesses are the extension point; templates second.
- Prefer adding a template or harness over adding core code.
- Harness CLIs may not emit `stream-json` — parsers must be tolerant (plain text fallback) and `extractResult` must synthesize from `streamedText` if no `result` line.
