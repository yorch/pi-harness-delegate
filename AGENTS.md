# AGENTS.md

Guidance for AI coding agents working in this repository.

`pi-harness-delegate` is a [pi coding agent](https://github.com/badlogic/pi-mono) extension that delegates work to multiple harnesses (Claude Code, Muse, OpenCode, Amp, Devin) headlessly. It ships as an npm package (`pi-package` keyword), installable with `pi install npm:pi-harness-delegate`.

> `CLAUDE.md` is a symlink to `AGENTS.md` — keep them in sync.

## Commands

| Command | What it does |
| --- | --- |
| `bun run typecheck` | `tsc --noEmit` over `extensions/`, `tests/` and `scripts/*.mjs` (strict, `allowImportingTsExtensions`, `checkJs` for the scripts) |
| `bun test` | `bun test` (bun:test — node:test compatible; `tests/live.test.ts` is opt-in, see below) |
| `bun run test:coverage` | `bun test --coverage` — text table + `coverage/lcov.info` (git-ignored). Informational only: no thresholds, not in `verify`/CI |
| `bun run lint` | `biome check .` (2 spaces, 120 cols, single quotes) |
| `bun run lint:fix` | `biome check --write .` |
| `bun run verify` | `lint + typecheck + test` — CI and release both run this |
| `bun changeset` | Create a changeset `.md` (commit it); `--empty` for docs/CI-only |
| `bun run version-packages` | Changesets bump + CHANGELOG (run by release workflow) |
| `bun run release` | `verify + check-packables + changeset publish` (OIDC) — `verify` here is the full lint+typecheck+test, not typecheck alone |
| `pi -e <path> -p "…" --no-tools` | Load local package as temp extension; smoke-tests manifest + factory |

CI (`.github/workflows/ci.yml`) runs `lint` + `typecheck` + `test` as separate steps (the same set `verify` bundles, so a green `bun run verify` locally predicts CI) + `check-packables` + changeset presence on every push/PR. Release (`.github/workflows/release.yml`) is changesets + OIDC trusted publishing — no npm token.

## Architecture

- `extensions/index.ts` — entry (factory only). Registers the read-only `delegate_modes` discovery tool (`makeModesTool()`, a typed `ToolDefinition<typeof MODES_TOOL_PARAMS, ModesToolDetails>` — see the modes.ts bullet), the `delegate` tool (primary) + `claude_delegate` alias — both built by one typed factory, `makeDelegateTool(name, spec)` (a `ToolDefinition<typeof DELEGATE_TOOL_PARAMS, …>`, no casts; the alias differs only in label/description/snippet and a pinned `forceHarness: 'claude'`) — (tool definition, `allowDangerous` confirmation, renderers), and `/delegate` command (primary) + `/claude`, `/codex`, `/opencode`, `/amp`, `/omp`, `/devin` aliases — the command handler (subcommand dispatch, parsing, the single-run `runOneDelegation` progress overlay) plus the `input`/`before_agent_start` hooks. The rest was split out mechanically, no behavior change: `engine.ts` (the engine below + `buildPrompt`/`fenceUntrusted`/`fenceScope`/`prLabel`/`untrustedNonce`, `runVerify`, `mergeAddDirs`, `saveOutput`, trust helpers `isProjectTrusted`/`warnIfProjectTemplatesSkipped`, `summarize`/`formatCost`, the queued report `injectReport`/`takePendingReport`, and the tool-path live-feed wrapper `runDelegateForTool`), `fanout.ts` (tool fan-out `runFanoutTool`, command fan-out `runFanoutCommand` → `runFanoutConcurrent`, `closeWhenMounted`; the command path's overlay state — `activeRunId`/`activeOverlay`, shared with `/delegate watch` — is a `RunUiState` object owned by the factory and passed in), `history.ts` (`/delegate history`), `subcommands.ts` (`list`/`status`/`config`/`config init`).
- `extensions/engine.ts` — reads `delegate` config (with legacy `claudeDelegate` migration), builds prompts, writes partitioned transcripts. **Prompt building** (see the scope-delimiting convention below): `buildPrompt(template, task, scope, cwd, harness, nonce?)` — the trailing `nonce` is injectable only so tests get a deterministic prompt; production omits it and each fence draws a fresh one via `untrustedNonce(content, random?)` (redraws until the candidate is absent from the content; `random` is injectable only to force a collision in tests). `fenceUntrusted(data, nonce?)` and `fenceScope(data, nonce?)` are exported (pure) — the former for external diff/PR/gh-stderr text, the latter for free-text scope — and both throw if a supplied nonce occurs in the data. `prLabel(target)` (exported, pure) normalizes a PR target to `#n`/`owner/repo#n` for the unfenced scope heading. `delegate()` is the shared engine — single source of truth for one harness run; everything else (fan-out, verify) is built on top of it, never around it. Resolves the transport via `resolveTransport(config, harnessName, harness)` (config.ts) **before** `acquireSlot()`/spawn — config override, falling back to the harness's own default, validated against `harness.supportsTransports` so an unsupported value (e.g. `transport: 'acp'` for `claude`) fails immediately with a clear message instead of a cryptic spawn error — then selects the runner at the one call site inside `delegate()` (`runHarness` for `'stdout'`, `runAcpHarness({...opts, harness: acpView(harness)})` for `'acp'` — `acpView`, in `acp-runner.ts`, presents the ACP-shaped fields of a dual-transport harness). The stdout call is byte-identical to before per-harness transport existed. **Slot lifetime**: the danger-permission refusal is resolved (pure) *before* `acquireSlot()`, and everything between the slot grant and the harness exiting (an abort re-check, `onAcquired`, scope resolution via `pi.exec`, `buildPrompt`, the runner) sits in one `try … finally { release() }` — a throw anywhere in that span used to leak the slot for the rest of the process (`tests/delegate-engine.test.ts`, which drives the exported `delegate()` with a fake `pi`/`ctx`).
  - **Verify**: after `delegate()` gets a result back from the harness (success or error-with-output), it resolves a verify command via `resolveVerifyPlan(opts.verify, template.verify, permission)` (activity.ts, pure — per-call override wins over the template's) and, if one is configured, either runs it host-side via `runVerify()` (`pi.exec('sh', ['-c', command], {cwd, timeout: VERIFY_TIMEOUT_MS})` — never delegated to the harness) or records it as skipped via `skipVerifyResult()`. **Trust model** (see the comment on `runVerify` in `engine.ts`): a verify command has exactly two legitimate sources — on-disk template frontmatter (project-local templates already gated by `isProjectTrusted(ctx)`, see below) or a human typing `/delegate --verify=<cmd>`. It is **not** a `delegate` tool parameter — `DelegateToolParams` deliberately omits it, because a tool param is model-settable and the model's context (repo content, delegated-harness output) is attacker-influenceable, making a model-settable `verify` a prompt-injection → arbitrary-host-command path. `resolveVerifyPlan` also never lets a configured command actually run when `permission === 'readonly'` (which includes a native read-only escape-hatch value such as `permission: plan` — `delegate()` resolves it to the `readonly` tier via `nativePermissionTier`, see the native-permission allowlist convention) — a `readonly` run's whole guarantee is "no execution/modification," so a verify command riding along on one would be a permission-tier bypass regardless of how trusted its source is; the skip is recorded (`### Verify: \`cmd\`` / `⊘ skipped (readonly run)`), never silently dropped. The `VerifyResult` is otherwise report-only: appended as its own section in the transcript (`buildTranscript`) and injected report (`buildReportContent`), and surfaced whole in the tool result's `details.verify` — it never touches `result.isError`. Skipped entirely (no section at all) when no command is configured (no invented default).
  - **Fan-out** (`harness: "all"` or a comma list, e.g. `"claude,codex"`): detected via `isFanoutSpec()` (command.ts). `resolveHarnessList()` (command.ts, pure) resolves the spec against `detectAll()` — `all` → every *detected* harness, an explicit list is alias/known-validated and also detection-filtered — uninstalled/unknown names are reported (`skipped`/`unknown`) rather than failing the run. The tool path (`runFanoutTool`) and the `/delegate` command path (`runFanoutCommand` → `runFanoutConcurrent`) both launch `delegate()` **concurrently, once per resolved harness**, all at once (`specs.map(...)` + `Promise.all`, not a sequential loop) — every call passes `waitForSlot: true`, so `acquireSlot` (concurrency.ts) is what actually bounds how many run at a time: it queues a run that doesn't fit under `maxConcurrent` instead of failing it, so a fan-out never exceeds the cap just because it launched everything at once. Each run writes its own transcript via the existing per-harness `outputsDir`. Results are collected (out of completion order) and reordered via `orderFanoutResults()` (activity.ts, pure) back to the resolved harness list before being mechanically assembled — no second model call — into one comparison report via `buildFanoutReport()` (activity.ts), which reuses `aggregateSpend`/`formatSpend` for the total-spend rollup (each row's metrics come from `runMetrics(details)` in engine.ts — the same helper the single-run command path uses, so rows report the real prompt-token figure); this keeps the report deterministic regardless of which harness actually finishes first. A `sessionId`/`--resume` combined with a fan-out spec is rejected up front on both paths via `fanoutResumeError()` (command.ts, pure) — a session id belongs to exactly one harness. A single-harness call is untouched by any of this (still `waitForSlot: false`, fails fast) — fan-out is purely additive, gated on `isFanoutSpec`.
  - **Notifications**: `/delegate all …` batches successful per-harness completions through `NotifyBatcher` (`extensions/notify.ts`) so the fan-out emits one debounced notification instead of one per harness; failures call `.failure()`, which flushes any pending batch and emits immediately — never delayed or batched. Since runs are concurrent, notifications now land in completion order, not resolved-harness order (only the synthesized report is order-normalized). Confined to the command handler's `ctx.ui.notify` path, guarded by `ctx.hasUI`; not a general event system.
- **Budget** (`maxBudgetUsd`): resolved once in `delegate()` (call → template → config → per-harness). `Harness.nativeBudget` (only claude: `--max-budget-usd`) means the CLI enforces it; otherwise both runners enforce it host-side via `isOverBudget()`/`budgetStoppedResult()` (`runner.ts`) — the moment a parsed result's running `totalCostUsd` exceeds the cap, the process is killed and the run finishes `isError: true`, `stopReason: 'budget_exceeded'`, `budgetExceeded: true` (ACP only checks once the new prompt is in flight, never during resume replay). **ACP specifics**: opencode's ACP final result only arrives with the `session/prompt` response — after the turn is already over — so a harness reports mid-turn spend through `ParseOutcome.runningCostUsd` (opencode: each `usage_update.cost.amount`) and `acp-runner.ts` checks that via `isCostOverBudget()`, killing mid-turn. That cost is *session*-cumulative, so the runner compares the **delta since this run started**: baseline `0` on a fresh session; on a resume, the last cost replayed before the prompt if any, else the first cost seen after it (under-counts that one step — deliberately biased toward never killing a resumed run for prior turns' spend); a resume that never saw a cost is never tripped. The reported `totalCostUsd` on an opencode-ACP resume is the delta over a *replayed* baseline only (`resumedRunCost()`), else `null` — see the opencode bullet. `describeBudget()` (`activity.ts`, pure) turns that into a `BudgetNote` (`native`/`host`/`unenforced` + message; `host` is always worded as best-effort — checked only at reported step/turn boundaries, can overshoot — never as a hard cap) recorded in `details.budget`, a transcript `- budget:` line, and prefixed to the returned `content` when there's something to say — a harness with no flag and no reported cost (codex, devin) is flagged `unenforced`, never silently ignored.
- **Timeout** (template `timeout:` / per-call `timeoutSec` tool param / `--timeout=<sec>`, all seconds): `resolveRunTimeoutMs(config, harness, template.timeoutSec, opts.timeoutSec, opts.timeoutSecMayRaise)` (config.ts, pure) — the configured timeout is **template > per-harness `harnesses.<name>.timeoutMs` > global `timeoutMs`**; a per-call value then **only lowers** it (`min`) unless `timeoutSecMayRaise` is set, which only the command paths do (`runOneDelegation`, `runFanoutConcurrent` — `--timeout=` is human-typed) — the tool path never sets it, so a model-set `timeoutSec` can't hold a slot past the user's config. Never unbounded: a call/template value is bounded `TEMPLATE_TIMEOUT_MIN_SEC..TEMPLATE_TIMEOUT_MAX_SEC` (10..7200) and re-clamped to the max here as defense in depth; config values are positive-only (`loadConfig`). A bad template value is ignored with a field warning at parse (`parseTemplateTimeout`, templates.ts — the author isn't there to ask); a bad per-call value is an error (`callTimeoutError`, templates.ts — checked in `delegate()`, up front in the tool's `execute()` before any confirm prompt so a fan-out fails once, and as a parser `errors` entry for `--timeout=`). Neither call nor template → exactly the old `per-harness ?? global`. The resolved value is in `details.timeoutMs` and a `- timeout: Ns` transcript line (`buildTranscript`'s `timeoutMs`). `--timeout=` accepts plain digits only (`/^\d{1,9}$/`) — never `Number()` coercion (`1e3`, `0x3c`, `+60`).
- **Template default harnesses** (template `harnesses:`): consulted **only** when the caller gave no harness (an explicit `--harness=`/first word/alias command/tool `harness` always wins). Which template copy decides is one shared rule, `templateForHarnessDefault(view, defaultHarness, mode)` (modes.ts — used by `templateForDefaults` in index.ts for both paths *and* by `collectModes`, so `delegate_modes` advertises exactly what a run does): the config `defaultHarness`'s own copy if its view has the mode (only that copy, `harnesses:` or not), else the first copy in registry order whose view has it **and** that declares `harnesses:` (a mode kept only under another harness's partition) — always one whole copy, never merged; views come from `templateViews(cwd, isProjectTrusted(ctx))`, the same trust gate as a run, and `templateHarnessDefault()` (command.ts, pure) turns its list into a normalized spec — **the same on both paths**: one name is a plain single run (`waitForSlot` unset, fail-fast at capacity); several are a fan-out spec handed to that path's *unchanged* fan-out runner — `runFanoutCommand` for `/delegate`, `runFanoutTool` for the `delegate` tool — so detection filtering + unknown/skipped reporting (`resolveHarnessList`), `waitForSlot: true` through `acquireSlot`, and `fanoutResumeError` all apply exactly as for a typed `a,b` list; no second concurrency mechanism. Both paths resolve the default *before* their confirm gates: the command's one `confirmDangerousCommand` names every resolved harness; the tool's `confirmDangerousToolCall` names the whole spec and `confirmToolAddDirs` gates the shared `addDirs` once for every harness that runs; both fail closed headless, before any detection probe or run. Why the tool fans out too, rather than narrowing to one harness for the model: the template is trusted on-disk config — user-global, or project-local only behind pi's trust store — exactly the trust level of `verify:`, so its author's "run this on these harnesses" is honored rather than silently narrowed for the model; the model sees the default up front in `delegate_modes`, can always pass an explicit `harness` to pin one, and per-run `maxBudgetUsd`/`maxConcurrent` still bound spend. `parseTemplateHarnesses()` rejects `all` (a template must name its harnesses — `all` would fan out to whatever happens to be installed) and non-name entries with a field warning; well-formed unknown names are kept for the run-time reporting. A template can't change permission through this.
- **addDirs**: three sources — the tool's `addDirs` param, repeatable `/delegate --add-dir=`, and template `addDirs:` frontmatter — merged by `mergeAddDirs()` (`engine.ts`: template first, then call, resolved against `ctx.cwd`, deduped; `undefined` when empty so argv is unchanged) and handed to the runner's existing `addDirs`. Per-harness limits stay where they were: codex drops them on resume, `opencode run` has no flag at all, ACP passes `additionalDirectories`.
- `extensions/validate.ts` — argv-injection guard + the danger confirmation gate. `sessionId` (`^[A-Za-z0-9._:-]{1,128}$`, no leading `-`), `model` (no leading `-`/control chars), `pr` (a number, an http(s) pull-request URL of the shape `<host>/<owner>/<repo>/pull/<n>` with no userinfo — any host, for GitHub Enterprise — or `owner/repo#n`), and `addDirs` entries (judged on their resolved, absolute form — what `mergeAddDirs` actually puts in argv — so a relative `-foo` is fine; empty/oversized/control-char entries are rejected) all land in a harness's (or `gh`'s) argv, are model-settable on the tool, and so are validated by `validateDelegateInputs()` at the top of `delegate()` (both paths) and up front in both fan-out paths — never left to each `buildArgs`. Where a CLI supports it, positionals also go after `--` (`codex exec resume --json [--model m] -- <id> <prompt>`, live-verified; `gh pr diff -- <target>`). `confirmDangerousToolCall()` gates the **tool** path's `allowDangerous: true`: a model-set flag is never honored alone — with `ctx.hasUI` it asks via `ctx.ui.confirm` (decline or a throwing dialog = refuse), without a UI it fails closed with a clear error. Checked once in `execute()` before single or fan-out dispatch. `confirmDangerousCommand()` is its human-typed counterpart for `/delegate --allow-dangerous`: same `askDangerConfirmation` primitive, the prompt names the harness(es), mode, and full/unrestricted permissions; one prompt for a whole fan-out (asked in `runFanoutCommand` after the harness list resolves, before `runFanoutConcurrent`); single runs ask in the command handler before `runOneDelegation`. Headless fails closed (fan-out refuses before even running `detectAll()`). Only an approval sets `allowDangerous: true` on the `delegate()` call — never `config.allowDangerous`. `confirmToolAddDirs()` applies the same gate to the tool's `addDirs`: `addDirsOutsideCwd()` resolves each entry against `cwd` and through symlinks (realpath, or the nearest existing ancestor's realpath for a not-yet-created path) on both sides, so neither `..` nor an in-repo symlink escapes; entries that stay inside `cwd` pass silently, anything outside needs `ctx.ui.confirm` and fails closed without a UI. Same one call site in `execute()` (covers single, fan-out, and the `claude_delegate` alias); template `addDirs:` and `/delegate --add-dir` never call it.
- `extensions/harnesses/types.ts` — normalized `NormalizedPermission = readonly|edit|danger`, `StreamedResult` (`numTurns`/`totalCostUsd` are `number | null` — `null` means the harness's payload didn't report the field, not a measured 0), `ActivityEvent` (`tool_input`/`tool_result` carry an optional `id` used to attribute a result to its originating call in a parallel batch), `ParseState`, `BuildArgsOpts`, `Transport = 'stdout' | 'acp'` (default `'stdout'` when a harness omits it — only `devin` sets `'acp'`), `DEFAULT_TIMEOUT_MS`. `Harness` interface: `name`, `binary`, `detect()`, `buildArgs()`/`parseLine()`/`permissionMap` (stdout transport), optional `buildAcpArgs()`/`parseAcpLine()`/`acpPermissionMap` (ACP transport — each falls back to its stdout-shaped counterpart when absent, so an ACP-only harness like Devin doesn't need to declare them twice), `extractResult()` (shared across both transports), `transport` (this harness's *default*), `supportsTransports?: Transport[]` (the *ceiling* `resolveTransport` validates config against — independent of the default; omitted means `[transport ?? 'stdout']`). `permissionMap` and `acpPermissionMap` are deliberately separate fields even when a harness's values happen to coincide (opencode) — they're different vocabularies (CLI arg fragments vs. ACP `session/set_mode` mode ids) that only look the same by day-one coincidence.
- `extensions/harnesses/claude.ts` — Claude Code runner: `claude -p --output-format stream-json --verbose` (+ `--no-session-persistence`/`--resume`), maps `readonly→plan`, `edit→acceptEdits`, `danger→bypassPermissions`. Wires `tool_use.id`/`tool_result.tool_use_id` into `ActivityEvent.id`. Schema verified against Claude Code 2.1.247.
- `extensions/harnesses/codex.ts` — Muse: `codex exec --json` + `--sandbox read-only|workspace-write|danger-full-access` (resume is the `codex exec resume <id> <prompt>` subcommand, not a flag — codex-cli dropped `--ask-for-approval` and `--thread-id` from `exec` entirely; `exec` is non-interactive by design so sandbox alone governs approval). Wires `item.id` (shared by `item.started`/`item.completed`) into `ActivityEvent.id`; `item.type` (e.g. `command_execution`) doubles as the tool name since items don't carry a `name` field. `turn.completed.usage` (`input_tokens`/`cached_input_tokens`/`cache_write_input_tokens`/`output_tokens`) is the real final-usage event — this codex-cli version never reports a `$` cost (ChatGPT-plan auth), so `totalCostUsd` stays `null`; `numTurns` is a genuine count of `turn.started` events, not a field the payload reports. Schema verified against codex-cli 0.149.1 — see `tests/fixtures/codex.jsonl`. **Resume live-verified end-to-end** against codex-cli 0.150.1 (`tests/fixtures/codex-resume.jsonl`): a first `codex exec` turn taught the model a fact and was killed; a second, independent `codex exec resume <id> <prompt>` process correctly recalled it — genuine cross-process context restore, not just an echoed session id. `codex exec resume --help` has no `--add-dir` at all (confirmed live: passing it is a hard CLI error, `unexpected argument '--add-dir' found`) — `buildArgs` only appends `--add-dir` on the fresh-turn branch, never on resume.
- `extensions/harnesses/opencode.ts` — OpenCode, the one **dual-transport** harness so far (`supportsTransports: ['stdout', 'acp']`, defaults to `'stdout'`). Stdout: `opencode run <prompt> --format json --agent plan|build[ --auto]` (this CLI version has no `--permission` or `--add-dir` flag at all — permission tiers map onto opencode's built-in agents instead: `plan` read-only, `build` full-access, `--auto` for danger-tier auto-approval; `addDirs` is silently unsupported). Wires `part.callID` into `ActivityEvent.id` — each tool call arrives as one already-resolved `tool_use` event (no separate pending/start line), so `tool_input`+`tool_result` are synthesized together from it. `step_finish.part.cost`/`.tokens` report *per-step* deltas, not a running total, so `totalCostUsd`/`usage`/`numTurns` are accumulated across every `step_finish` seen in the stream. `totalCostUsd` stays `null` unless at least one `step_finish` actually carried a numeric `cost` (`costSeen`) — a step without one is unmeasured, not $0. Schema verified against opencode 1.18.16 — see `tests/fixtures/opencode.jsonl`.
  - **ACP** (`buildAcpArgs` → `['acp']`, no `--model` — `opencode acp --help` has no such flag): `parseOpencodeAcpLine` translates the same `session/update` dialect as `devin.ts` (real, live-verified: opencode's compiled binary shares an ACP implementation with omp — see `docs/acp-harness-assessment.md` §2), kept as an independent function rather than a shared import so `devin.ts` needs zero changes. Genuine gains over stdout: real `contextWindow`/`cost` (latched from the *last* `usage_update` seen — server-side running total per session, not summed like `step_finish` — `usage_update.cost.amount`/`.size`; because it's session-cumulative, a resumed run's reported `totalCostUsd` is the delta since the same baseline the host budget check uses — `resumedRunCost()` in acp-runner.ts — so `/delegate status` never double counts prior turns, and is `null` when that delta can't be measured — including whenever no cost was replayed before the prompt, since a first-post-prompt-sample baseline would silently omit that first step's spend; the budget check keeps using that baseline regardless), and a `sessionId`/`session/load` resume path independently proven to recall cross-process state (`tests/fixtures/opencode-acp.jsonl`, including a same-process `session/load` replay). `model`/`numTurns` stay `null` — never confirmed back over ACP, unlike Devin's `agent_stopped` event. **The one thing this needed a live run to close**: does opencode's `build` mode (where `edit`/`danger` both land) ever call `session/request_permission` for a write — which `acp-runner.ts`'s defensive client auto-declines? A second live run answered no — a real write prompt under `build` produced a `tool_call`/`tool_call_update` with `kind: "edit"` and no permission request at all (`tests/fixtures/opencode-acp-build-write.jsonl`), so `edit`/`danger` genuinely execute over ACP. `acpPermissionMap` (`plan`/`build`/`build`) is a separate field from `permissionMap` even though the values coincide today — see the types.ts bullet.
- `extensions/harnesses/amp.ts` — Amp/Omp: `<binary> -p --mode json --approval-mode always-ask|write|yolo`, alias `omp→amp`. **`omp` here is "Oh My Pi", a `pi`-framework-based CLI — not a drop-in rebrand of Sourcegraph's Amp** (confirmed via `omp --help`: entirely different flag surface, e.g. `--mode`/`--approval-mode` vs. the real Amp CLI's assumed `--output`/`--permission`). It's simply the only binary of this harness installed on the capture machine, and its JSONL envelope (`session`/`turn_end`/`agent_end`/…) is what got captured and wired; behavior against the real Sourcegraph `amp` CLI is unverified. `binary` resolves to whichever of `amp`/`omp` actually exists on `PATH` at module load (`resolveAmpBinary`) — previously it was hardcoded to `'amp'`, so a machine with only `omp` installed could never actually spawn this harness despite `detect()` reporting it as available. Wires `toolCallId` into `ActivityEvent.id`. `message.usage.cost.total`/`.input`/`.output` on `turn_end` are per-turn, not cumulative (confirmed: three real turns each reported similar-magnitude token counts, not compounding ones) — accumulated across every `turn_end` for a genuine session total; `totalCostUsd` is `null` unless some `turn_end` actually carried a numeric `usage.cost.total` (`costSeen`); `agent_end` reads the same accumulator rather than re-deriving from `o.message` (which doesn't exist on `agent_end` — it's `o.messages`, an array — a bug that silently nulled out the final result before this fix). Schema verified against omp 17.2.9 — see `tests/fixtures/amp.jsonl`. **A `turn_end`/`agent_end` where `message.content` is empty and the failure only shows up as `message.stopReason === "error"` + `message.errorMessage` (a real 429 quota rejection, `tests/fixtures/amp-error.jsonl`) used to be silently reported as a successful empty-text run** — the top-level `is_error` field this parser checked is never set on this shape — fixed to also treat that message shape as `isError: true` with `errorMessage` as the result text. `--add-dir=<value>` is real and repeatable per `omp --help` (confirmed live: a run with `--add-dir` echoed the directory back in the session line's `additionalDirectories`) — earlier research had flagged it as possibly absent from `omp --help`; that was wrong for omp 17.2.9. `supportsTransports: ['stdout']` only — `omp acp` is real and live-verified, but its ACP mode surface has only 2 tiers (`default`/`plan`) against the stdout `--approval-mode`'s genuine 3 (`always-ask`/`write`/`yolo`); offering `transport: 'acp'` at all would let a user silently lose the `edit` tier's distinct semantics, so it's not a legal config value (`docs/acp-harness-assessment.md` §5).
- `extensions/harnesses/devin.ts` — Devin over the Agent Client Protocol (`devin acp`), not stdout JSONL: `transport: 'acp'`, `buildArgs` returns `['acp']` plus `['--model', opts.model]` when a model is resolved (prompt/permission/session lifecycle are otherwise all negotiated over the wire by `acp-runner.ts`, not CLI flags). - `extensions/acp-runner.ts` — sibling to `runner.ts` for the `'acp'` transport (devin, always; opencode, when configured). ACP (https://agentclientprotocol.com) is JSON-RPC 2.0 over stdio, bidirectional and stateful, unlike the stdout harnesses' one-way JSONL stream — `runAcpHarness(opts)` exposes the exact same `RunHarnessOptions`/`HarnessResult` shape as `runHarness` so `delegate()` and everything downstream (transcripts, `ToolCallIndex`, overlays, fan-out, spend) is unchanged. `acpView(harness)` (exported) presents the ACP-shaped fields of a dual-transport `Harness` (`buildAcpArgs`→`buildArgs`, `parseAcpLine`→`parseLine`, `acpPermissionMap`→`permissionMap`) to this file, falling back to the stdout-shaped names for an ACP-only harness like Devin — this file itself always reads the stdout-shaped field names and needed zero changes for that split. Drives the handshake (`initialize` → `session/new` or `session/load` when `opts.resumeSessionId` is set → `session/set_mode` → `session/prompt`). `initialize`'s negotiated `protocolVersion` is checked against what was sent and fails clearly on a mismatch (only `1` has ever shipped, so this is currently inert insurance, not observed behavior). `session/set_mode` is capability-checked first via `supportsSessionModes()` — true if `session/new`/`session/load`'s response has the spec-standard `modes` field (Devin, omp) **or** a `configOptions` entry with `category: "mode"` (opencode, which never populates `modes` but implements `session/set_mode` anyway; omp has both) — and if neither signal is present, the run fails immediately with a clear message rather than either calling a method the agent may not implement or silently running at the agent's default (unconfirmed) permissiveness; every real agent captured so far advertises one of the two signals, so this never fires today. Holds `stdin` open for the run (with a no-op `stdin.on('error')` so a write to an agent that already exited — an async EPIPE — can't crash the host) (`stdio: ['pipe','pipe','pipe']` — the existing stdout harnesses use `'ignore'`; ACP agents exit on stdin EOF), and shares `runner.ts`'s 5MB `streamedText` cap / 5000-activity cap (`stream-caps.ts`) and mirrors its timeout/AbortSignal-kill behavior. Every incoming line is fed through `harness.parseLine` (same as `runner.ts`) in addition to the runner's own request/response correlation (a `Map<id, PendingRequest>`, each handshake step bounded by `HANDSHAKE_TIMEOUT_MS` (overridable only via the test-only second `internals` argument, `runAcpHarness(opts, { handshakeTimeoutMs })` — which also takes a `spawn` replacement, used only to inject the stdin EPIPE `'error'` event bun never emits for a real closed pipe, so the stdin error guard has a test that fails without it) separate from the overall `timeoutMs` so a hung handshake fails fast instead of wedging the whole budget). Two gotchas found only by running it, not reading the spec: (1) the agent does **not** exit once `session/prompt` resolves — an ACP session can outlive one turn (resume, follow-up prompts) — so the runner explicitly `finish()`es off `state.result` as soon as the response resolves and kills the process itself, rather than waiting for `proc.on('close')`, which could hang indefinitely; (2) `session/load`'s response carries no `sessionId` of its own (unlike `session/new`'s), so the runner stashes `opts.resumeSessionId` into `state._harness` itself so the harness's `parseLine` can still report it on the final result. Server-initiated requests (permission prompts, fs reads) get a defensive, always-answered response — `session/request_permission` picks a `reject_once`/`reject_always` option (or `cancelled` if none), everything else gets a JSON-RPC error — since we run non-interactively with a mode already negotiated; never observed in the captured fixture, but every request needs a reply or the agent hangs. **Every exit path kills the child process** — timeout, abort, success, and (as of the process-leak fix) a rejected handshake step too: the handshake IIFE's `.catch` now `proc.kill('SIGKILL')`s before `fail()`s, matching the other three paths; without it, ACP agents (stdin-EOF-only exit, never sent on this path) leaked indefinitely — confirmed live both ways with the same repro (`session/load` against a nonexistent `sessionId`, which devin genuinely rejects with a JSON-RPC error). **Resume discards replayed history**: `session/load` replays every prior turn as `session/update` notifications before the new prompt's; a `promptSent` flag (set only once `session/prompt` is actually sent) gates whether `parseLine`'s `streamedText`/`activities` output is forwarded to `state`/`onStream`/`onActivity`, so replayed content from a resume never reaches the caller — verified live: a fresh process resuming a session created by an earlier one returned only the new turn's answer, while still correctly recalling information only given in the first turn.

- `extensions/run-registry.ts` — file-based active-run registry (`acquireRun`/`releaseRun`/`countActiveRuns`) under `<agentDir>/delegate/runs/`, one JSON file per active run, so the concurrency guard and `/delegate status` active count are accurate across pi processes, not just the current one. Entries are written atomically (`<entry>.json.tmp` + `renameSync`) and readers only consider `.json` files — previously a reader could catch a half-written entry, treat it as corrupt, and delete a live run's registration. Best-effort (never throws); stale entries from dead pids *and* entries with a corrupt/non-numeric `pid` are cleaned up on read (`process.kill(pid, 0)`, treating `EPERM` as alive). Entries are written as `<pid>-<harness>-<rand>.json.tmp` then renamed; `countActiveRuns` never counts a `.json.tmp`, but reaps one whose embedded pid is dead (or unparseable) or whose mtime is older than `STALE_TMP_MS` (60s) — a writer that crashed between write and rename would otherwise leave it forever. `concurrency.ts` combines it with an in-process counter via `Math.max` as a fallback. `acquireRun`/`countActiveRuns` alone are still a plain, racy check-then-act pair — kept as-is for callers (e.g. `/delegate status`) that don't need the cap enforced. `acquireRunWithinLimits(harness, mode, maxGlobal, maxPerHarness)` is the one that closes that race for `acquireSlot`: it writes, then re-reads the registry to confirm the write didn't push either limit over the top, undoing it if so — a write-then-recheck instead of check-then-write, which makes over-admission (the cap standing exceeded for a run's whole lifetime) impossible by construction. It's still not a hard mutex: a tight multi-way race can make more than one contender see each other's just-written entry and *both* back off even though one could have fit — a transient under-admission that self-heals on `acquireSlot`'s poll loop, never an over-admission. A failed row keeps the failure reason (or its last activity) as its activity text instead of blanking — the moment a row goes red is exactly when its context matters. `isFanoutComplete(rows)` (pure) is true once every row is terminal; `multiProgressWindow` uses it to switch Esc/`m` from "arm cancel"/"minimize" to an immediate dismiss once there's nothing left to cancel, which `runFanoutConcurrent` (`fanout.ts`) pairs with a `FANOUT_LINGER_MS` (~3s) post-completion linger before it tears the overlay down on its own — run detached after `runFanoutConcurrent` returns its outcomes, so the linger never delays the caller or the injected report; an explicit cancel skips the linger since it already signals "done watching."
- Subcommand UIs in `subcommands.ts` (`list`/`status`/`config`) and `history.ts` (`history`), dispatched from `index.ts`'s handler: `/delegate list [harness]` (rows from `collectModes`/`formatModeRow`, modes.ts — the same sanitized data the `delegate_modes` tool shows), `/delegate history` (partitioned, with scrollable viewer + resume, legacy dir filtered for `-partial` transcripts same as the partitioned dirs), `/delegate status` (per-harness spend rollup via `aggregateSpend`, e.g. `$1.234 over 12 run(s) (3 unknown)` — unknown-cost runs are never folded into the total silently; now leads with `describeConfigSource()`'s provenance line(s) instead of jumping straight to resolved values), and `/delegate config` (`showConfig`, print-only — `buildConfigReport()`'s provenance + raw-file-JSON + effective-JSON, in the same scrollable-overlay-or-stdout pattern as `status`) plus `/delegate config init` (`initConfig`, the one place this extension writes to `settings.json`, and only on this explicit subcommand — calls `writeDelegateConfig()` with the current effective config; also the practical fix for the legacy-`claudeDelegate`-only gap, since writing an explicit `delegate` key makes it win from then on without touching `claudeDelegate` itself). The `active` column shows `activeCount(h)/getMaxConcurrent(cfg, h)` (`∞` when the cap is `0`) so a `maxConcurrent: {perHarness: {...}}` override is visible per-row instead of only in the raw JSON in the header; the global summary line does the same for `getMaxConcurrent(cfg)`.
  `list`/`history` share one `filterHarness` closure over `resolveHarnessFilter()` (command.ts, pure) to resolve their optional harness word/`--harness=` flag — this is what makes them agree on alias (`omp`→`amp`) and case handling, a thing they used to parse independently and could drift on. An unrecognized harness word now reports itself and the valid list (`ctx.hasUI` ? `notify` : stdout, matching the rest of the file's headless-vs-TUI convention) instead of one subcommand silently showing an unfiltered list and the other silently showing an empty one. `showHistory`'s header (both the plain-text and the `SelectList`-backed TUI path) now names the active filter, matching `showModes`/`showStatus`.
- `PI_CODING_AGENT_DIR` (pi's own agent-dir override, read via `config.ts`'s `agentDir()` and `templates.ts`) relocates everything this extension keeps under `~/.pi/agent` — `settings.json`, user templates, `delegate/outputs/`, `delegate/runs/`. Tests set it to a temp dir — and the `bun test` preload (`tests/helpers/preload.ts`, via `bunfig.toml`) pins it to a fresh `os.tmpdir()` dir for the whole test process, so even a straggling run after a sandbox restore never touches the real `~/.pi/agent`. Live mode (`PI_DELEGATE_LIVE=1`) is pinned too: `tests/live.test.ts` hands the outer value (`preloadState().outerAgentDir`; absent when it was unset) to the real harness CLIs' child processes only, since `omp` reads the same var for its own auth: it swaps env with the synchronous `withEnvSync` (`tests/helpers/env.ts`) around just the call that spawns the child (`spawn` snapshots `process.env` when called, and both runners spawn synchronously), so this process is re-pinned before the run is even awaited — never an async `withEnv` held across the run, which restores only once the run settles, i.e. possibly after bun's per-test timeout moved on, and overlapping restores then leave the process unpinned (`tests/preload.test.ts` "live swap" pins both behaviours) — so an unfiltered live run can't leave other files unpinned (the preload can't see the command line: inside it, `process.argv` names only the first test file). The pinned dir is removed on exit and on SIGINT/SIGTERM/SIGHUP (cleanup, then the signal is re-raised) — the signal path only when the preload is that signal's sole listener; with another listener the process isn't killed by it, so removing the dir would strand the ongoing run, and the exit handler cleans up instead. bun reads `bunfig.toml` only from its cwd, so run `bun test` from the repo root (`bun run test` works anywhere); `tests/preload.test.ts` asserts a marker the preload sets and fails loudly without it — never import the preload from a test (shared bits live in the side-effect-free `tests/helpers/preload-state.ts`), or a missing preload gets silently patched. Documented in README (Config) and CONTRIBUTING.
- Config surface: `modelAliases` (`economy/balanced/max`), `maxConcurrent` (global + per-harness, default `4` — genuinely parallel now, not just "don't overlap": see the Fan-out bullet above), `maxTranscripts` (`pruneOutputs` per harness).
- `extensions/usage.ts` — maps harness usage/cost to pi `Usage` (cacheCreation folds into input). `mapHarnessUsage`/`mapClaudeUsage` always return a `Usage`, reporting `cost.total: 0` when the harness didn't report cost (Codex, Devin) — a deliberate, bounded exception because `Usage.cost.total` is mandatory and losing those harnesses' tokens from pi's session totals is worse than under-reporting spend by a known amount. Do **not** generalize this `null -> 0` fallback elsewhere: `StreamedResult.totalCostUsd` stays `number | null` everywhere else, transcripts render `cost: —`, and `/delegate status`'s `aggregateSpend` still counts unknown-cost runs separately. See the README's "Metrics recorded" section.

## Conventions

- **2 spaces**, single quotes, 120-col lines — enforced by Biome (`biome.json`: 2 spaces, 120, singleQuote, trailing all). Run `bun run lint:fix` if a diff looks unformatted.
- TypeScript strict; explicit types on exported functions.
- Relative imports **must include `.ts`** (`./runner.ts`) — jiti + `allowImportingTsExtensions`.
- **Templates live as .md files with frontmatter**, never as code strings. Frontmatter: `name, description, permission: readonly|edit|danger, model, maxBudgetUsd, skill, defaultTask, defaultScope`. Legacy `permissionMode`/`sandbox` preserved as native escape hatch.
- **Never default to `danger`.** Only path is explicit `allowDangerous:true` on a call — from the tool (model-set, human-confirmed) or `/delegate --allow-dangerous` (human-typed, still human-confirmed, refused headless). Never inherited from `config.allowDangerous`; the command flag applies to that one invocation only and must never become a tool parameter. `review`/`plan`/`security-audit` stay `readonly`.
- Guard UI calls (`ctx.ui.*`) with `ctx.hasUI` — tools run in all modes.
- Scope `diff`/`pr` resolved in-process via `git diff HEAD` / `gh pr diff`; don't rely on harness running git.
- **Unmeasured metrics are `null`, never a fake `0`.** `numTurns`/`totalCostUsd` on `StreamedResult` and `cost` on `parseTranscriptMeta` are `number | null` — `null` means the harness's payload didn't report the field. Render `null` as `—`/`n/a` (`formatMetrics`, `buildTranscript`, `/delegate status`, `/delegate history`), never `0`/`$0.000` — a real `$0` run and an unmeasured run must stay visually distinct.
- **Verify is report-only, trusted-source-only, and never on `readonly`.** A `verify` command (frontmatter `verify:` or the `/delegate --verify=` flag) runs host-side after the harness exits and its pass/fail is recorded alongside the result — it must never flip `isError`, which stays exactly what the harness itself reported. Never invent a default verify command for a template. **`verify` is not, and must never become, a `delegate` tool parameter** — a tool param is model-settable, and the model's context (repo content, delegated-harness output) is attacker-influenceable, so that would be a prompt-injection → arbitrary-host-command path; the only legitimate sources are on-disk template frontmatter and direct human input. A verify command must also never actually execute on a `permission: readonly` run — that would silently break `readonly`'s no-execution guarantee — so `resolveVerifyPlan` always skips it there (recorded, not dropped) regardless of who configured it.
- **`allowDangerous` on the `delegate` tool always needs a human.** `confirmDangerousToolCall` (validate.ts) — interactive confirm, or fail closed with no UI. Never inherit it from config, never auto-approve. `/delegate --allow-dangerous` goes through the same gate (`confirmDangerousCommand`) — one confirm per invocation (one for a whole fan-out), fail closed headless.
- **Model-settable params may only narrow, never widen, resource limits.** Next to `allowDangerous` (needs a human), `addDirs` (outside cwd needs a human) and `verify` (not a tool param at all): the tool's `timeoutSec` can only *lower* the configured run timeout (`resolveRunTimeoutMs` takes `min` unless `timeoutSecMayRaise`, which only the human `/delegate --timeout=` paths set). A widening model-set limit would let a prompt-injected model hold every `maxConcurrent` slot for the cap's full length. Any new model-settable limit follows the same rule; human-typed flags and on-disk template frontmatter keep the full range.
- **Model-supplied `addDirs` outside the working directory always need a human.** `addDirs` widens what a harness can touch (codex/claude/amp `--add-dir` is writable on non-readonly runs; even `readonly` can read it), and a tool param is model-settable, so it's the same prompt-injection trust model as `allowDangerous`/`verify`. `confirmToolAddDirs` (validate.ts) lets entries that resolve inside `cwd` (after `..` and symlink resolution) through and gates everything else behind an interactive confirm, failing closed with no UI. Template frontmatter (trusted on-disk config) and the human-typed `/delegate --add-dir` stay unrestricted. Never relax this to a raw string-prefix check — resolve symlinks.
- **Scope content is always delimited in the prompt; the task is not.** `buildPrompt` (engine.ts) takes a `ScopeSection {heading, data?, kind?}` — `heading` is our own fixed text, and `data` is delimited according to `kind`, both via one shared mechanism: a backtick fence strictly longer than the longest backtick run in the data, between `BEGIN/END <LABEL> <nonce>` markers with a random nonce verified absent from the data. Two kinds, because scope plays two different roles:
  - `'untrusted'` (the **default** — anything not explicitly marked fails safe to it): genuinely external text the harness should *analyze* — `git diff`, a `gh pr diff` body, gh's stderr. `fenceUntrusted()` (`UNTRUSTED DATA` markers) plus a "data, not instructions — analyze it as input" note. A malicious PR controls its own diff.
  - `'restriction'`: free-text scope (`--scope src/a.ts, src/b`, the tool's `scope` param, a template's `defaultScope`). Its whole job is to *narrow* the work, so the untrusted fence's "analyze it as input" framing would turn a restriction into inert data (the bug this split fixes). `fenceScope()` (`SCOPE` markers) frames it as "restrict your work to it" — but it is still delimited and explicitly limited to narrowing, never adding tasks, granting permissions or changing role, because it is not trustworthy enough to be an instruction: the tool param is model-set (the model's context is attacker-influenceable) and `defaultScope` comes from a template file. We deliberately don't distinguish the human `--scope` source here — `delegate()` can't tell sources apart without threading provenance through, and the restriction-only framing is correct for all of them.

  A PR target never reaches the (unfenced) heading raw: `prLabel()` reduces it to `#n`/`owner/repo#n` from strict-charset parts (a validated PR URL may still carry any `\S*` tail). Never interpolate PR/diff/scope text raw into the prompt, and don't fence the user's `task` (it *is* the instruction). Tests: `tests/prompt.test.ts`, `tests/delegate-engine.test.ts`.
- **Legacy `permissionMode:`/`sandbox:` keys fail closed.** They're only read when `permission:` is absent (`permission:` always wins, and its unknown-value native escape hatch is unchanged; a legacy key that disagrees with a normalized `permission:` tier is ignored but recorded in `permissionWarning` — `legacyOverrideWarning()` stays quiet only when *every* ignored legacy value is recognized and maps to exactly the running tier, so an unrecognized one, or ignored keys that disagree with each other (`sandbox: read-only` + `Sandbox: workspace-write` next to `permission: readonly`/`plan`, where the least permissive still matches), are flagged too; in the conflicting-`permission:` branch the same note is appended (`…; permission: readonly overrides …`) against the tier that branch resolved to, rather than the legacy keys being dropped silently; next to a *native* `permission:` value, whose tier is only known per harness, `parseTemplate` instead carries the ignored keys as `ignoredLegacyPermission` and `delegate()` judges them via `nativeOverrideWarning()` against the tier that value actually runs at on the resolved harness — `nativePermissionTier`'s readonly, else edit, or danger for a `danger`/`unlisted` value — surfacing the same warning on every channel below; report-only, the tier never moves. That `(<tier> on <harness>)` label is what the template's native value means on that harness, deliberately *not* the tier a per-call `allowDangerous` escalation actually ran at — the warning is about the template's own keys, and the escalation is already visible in `details.permission`/argv (pinned by a test in `tests/delegate-engine.test.ts`); `template.permissionWarning ?? nativeOverrideWarning(…)` never hides a native warning, because the two are mutually exclusive — `ignoredLegacyPermission` is only set on the single-`permission:` native path, which sets no `permissionWarning`, and the conflicting-`permission:` branch keeps no native value). `normalizeLegacyPermission()` (templates.ts) accepts both vocabularies under either key, case/whitespace/`-`/`_`-insensitive: claude `PermissionMode` names (`plan`→readonly, `bypassPermissions`→danger, the rest→edit; separators are dropped only for this lookup, so `accept-edits` can only ever mean `acceptEdits`) and codex sandbox values (`read-only`→readonly, `workspace-write`→edit, `danger-full-access`→danger, gated by `allowDangerous` like any danger template). The three permission *key names* are matched case-insensitively in `parseTemplate` and every occurrence is kept (`Sandbox:` used to be silently ignored → `edit`): several legacy values → the least permissive tier; several disagreeing `permission:` values → the least permissive tier, or `readonly` if a native value is involved (not rankable at parse time), both with a warning. An **unrecognized** value loads the template as `readonly` with `permissionWarning` set (prefixed to `description` as a `⚠` so `/delegate list` shows it; `delegate()` also repeats it on every run — `ctx.ui.notify`/stderr, a `- warning:` transcript line, a `content` prefix and `details.permissionWarning`; echoed values — and the template name in the `⚠ template "…":` prefix and the danger-refusal error — go through `quoteValue()` (templates.ts; escapes the shared `sanitize.ts` set as `\uXXXX` — see that bullet); a template's `description:` (which carries that `⚠ … ·` prefix) and its name are only displayed via mode discovery, which strips the same set through `sanitizeTemplateText()`/`sanitizeIdentifier()` — the transcript `mode:` line still shows the name as written; echoed *keys* use the author's own spelling (`Sandbox`, `SANDBOX`) via `displayKey()`, which only accepts a plain `[A-Za-z_]` case variant of the canonical key (capped at 32) and otherwise falls back to the canonical name — frontmatter keys in a hostile project template are attacker-influenceable too) — never the old silent `edit` (which made `sandbox: read-only` run as workspace-write *and* execute its `verify:` host-side). Deliberately not "refuse to load": `loadDir` skips unparsable files silently and a dropped override lets a same-named lower tier (builtin `implement` is `edit`) run in its place — possibly wider than the author meant; `readonly` is the one tier that can never exceed any author's intent, and it also skips `verify`. Never map an unknown legacy value to anything wider than `readonly`.
- **Native permissions are an allowlist, not a denylist.** A template's `permission: <native>` escape hatch is non-danger only if it's in that harness's `safeNativePermissions` (types.ts; populated per harness from its real `--help`/ACP `availableModes`). `classifyNativePermission` (registry.ts) returns `none|safe|danger|unlisted`; `isNativeDangerPermission` is `danger || unlisted`, so an unknown or newly-added permissive mode (claude `auto`, devin `smart`, a custom opencode agent) fails closed behind `allowDangerous`. A confirmed `unlisted` value runs as declared (engine.ts keeps it as `nativePermissionForRun`) instead of being widened to the harness's danger mode. Matching is whitespace-trimmed and **case-insensitive**, danger checks first (so `Yolo`/`BYPASSPERMISSIONS` stay `danger`); a `safe` match is rewritten to the allowlist's canonical spelling via `canonicalSafeNativePermission` (registry.ts) before it reaches argv/ACP — never emit the template's own casing (CLIs are case-sensitive, claude's `acceptEdits` is camelCase, and a custom opencode agent `PLAN` must not run in place of the built-in `plan` it was classified as). When a harness CLI gains a new restrictive mode, add it to the allowlist — never add a permissive one. The allowlist's genuinely read-only subset is `readonlyNativePermissions` (types.ts — claude/devin/opencode `plan`, codex `read-only`; amp `always-ask` deliberately not, since `-p`'s handling of an unanswerable ask is undocumented): `nativePermissionTier` (registry.ts) maps such a value to the `readonly` tier, which `delegate()` uses as the template's effective tier — so it's recorded as `readonly` (`details.permission`, transcript) and `resolveVerifyPlan` skips its `verify:` — while the canonical native value still reaches argv/ACP unchanged. Only list a mode whose no-write behavior is documented for a non-interactive run.
- **Validate anything argv-bound at the shared entry.** New model-settable params that reach a CLI's argv go through `validateDelegateInputs` (no leading `-`), not ad-hoc checks in a harness.
- **Fan-out never bypasses the concurrency guard — it queues through it instead of failing.** `harness: "all"`/a comma list launches `delegate()` concurrently for every resolved harness (`Promise.all`), each passing `waitForSlot: true` to `acquireSlot` (concurrency.ts) so a run beyond `maxConcurrent` waits for a slot instead of erroring out. A single-harness call must keep `waitForSlot` unset/`false` — it should still fail fast (`ConcurrencyLimitError`) at capacity, exactly as before this existed. Do not add a second, independent concurrency limiter (e.g. a fixed-size worker pool) alongside `acquireSlot` — it's already the one bounded-pool primitive; reuse it.
- **Mode discovery is read-only and shows data, not instructions.** `delegate_modes`/`/delegate list` (modes.ts) never take a slot, spawn (use `onPath`, never `detect()`), write, or notify; never include project-local templates unless `isProjectTrusted(ctx)`; and expose only an allowlist of fields — never a `verify:` command, prompt body, `defaultTask`/`defaultScope` text or paths. Any new template-authored field shown there goes through `sanitize.ts` (`sanitizeTemplateText()`, or `sanitizeIdentifier()` for a name) and, in the model-facing text, is quoted and labelled as data. Listing order and caps are per source tier — never a single global cut a project's templates could fill.
- **A template's `harnesses:` is a default, never an override, and only ever reaches the existing fan-out paths.** It applies only when no harness was given; several names go through `runFanoutCommand`/`runFanoutTool` exactly like a typed list (`resolveHarnessList`, `waitForSlot: true`, `fanoutResumeError`), resolved before the confirm gates so they cover every harness that runs. Never let a template widen permission, pick a harness when the caller named one, accept `all`, or bypass `acquireSlot`/the confirm gates.
- **No template variable substitution.** Templates are static prompt bodies; the task and fenced scope are appended by `buildPrompt`. Don't add `{{task}}`-style interpolation without revisiting the scope-fencing convention above.
- **Tests restore env vars delete-when-unset, via the helper.** Set/restore env in tests only through `withEnv()`/`restoreEnv()` (`tests/helpers/env.ts`) — never `process.env.X = prev`: when `X` was unset, `prev` is `undefined` and Node/Bun store the string `"undefined"` (a restored `PI_CODING_AGENT_DIR="undefined"` once wrote a straggling run's transcript into a relative `undefined/` dir in the repo). `tests/env-hygiene.test.ts` fails on any use of `process.env`/`Bun.env`/`import.meta.env` other than an allowlisted read in another source file of any JS/TS flavour under `tests/` (`fixtures/` included) — an allowlist of reads (value reads of `env.X`, and the bare object only in `in`, spread, a `{ env: … }` option, `Object.keys`-style calls, `const { A } = env`, `typeof`) rather than a denylist of write shapes, because enumerating writes kept missing some (parenthesised/destructuring targets, `Object['assign']`, `Reflect.apply`, …); it bans bare `process`/`Bun` values, `= globalThis` aliasing and env imports from `process`/`node:process`/`bun` outright, and scans whole files with comments and string/regex text stripped (`${…}` bodies stay code; a would-be regex that could hide env code is kept as code); only `helpers/env.ts` is exempt (the preload sets its pin through `restoreEnv` too). A preload `afterEach` is the runtime backstop: any env value exactly `"undefined"`/`"null"` after a test fails that test (and is removed) — a backstop, not a proof. When adding a write shape the scan misses, add it to the detector's self-test table. Because of the preload, `prev` for `PI_CODING_AGENT_DIR` is the pinned temp dir, never `undefined` — don't add tests that depend on it being unset outside a `withEnv({ PI_CODING_AGENT_DIR: undefined }, …)` block.

## Git workflow

- **Always work in a git worktree** for any new work (feature, fix, docs, refactor), unless the user explicitly says not to. Never edit directly on the `main` checkout. Create the worktree before touching files, and do all commands from inside it.
- **Use [Conventional Commits](https://www.conventionalcommits.org/)** for every commit message *and* PR title: `type(scope): summary` — e.g. `feat(fanout): …`, `fix(acp-runner): …`, `docs: …`, `chore: …`, `test: …`, `refactor: …`. Scope is optional; keep the summary imperative and lowercase.
- **Commit in logical groups** — each commit is one coherent change that makes sense (and ideally passes `bun run verify`) on its own, e.g. implementation, tests, docs, and the changeset as separate commits when they're independent. Don't lump unrelated changes into one commit, and don't split one change across many tiny ones.

## Release process (changesets + OIDC)

Changesets + OIDC trusted publishing. No manual `version` bump, no `npm publish`.

1. Edit code → `bun run verify`.
2. `bun changeset` (or `bun changeset --empty` for docs/CI) → commit `.changeset/*.md`. **Important:** `package.json:files` includes `README.md` (and `templates/` for this repo), so even README/docs-only PRs are considered a package change — `ci: Changeset present` (`changeset status --since=origin/main`) will fail without a changeset. For docs-only that should not bump the version, run after `bun install`:
   ```bash
   bun install
   ./node_modules/.bin/changeset add --empty   # creates .changeset/*.md with ---/--- (no bump)
   git add .changeset/*.md && git commit
   ```
   This satisfies CI with `Packages to be bumped:` empty.
3. PR → CI checks `changeset status --since=origin/main`.
4. Merge to `main` → Release workflow opens/updates `chore: version packages` PR (bumps `package.json` + `CHANGELOG.md`).
5. Review version numbers → Merge Version Packages PR → Release workflow runs `bun run release` (`verify + check-packables + changeset publish`), creates tag `vX.Y.Z` pinned to `$GITHUB_SHA` + one GitHub Release, verifies `latest` dist-tag.
6. On machines with the package installed: `pi update --extensions`.

Load-test a local change: `pi -e <repo path> -p "Reply with exactly: OK" --no-tools`. Engine can be exercised without pi: `bun --input-type=module -e "import {runHarness} from './extensions/runner.ts'; import {claudeHarness} from './extensions/harnesses/claude.ts'; …"`.

Load-test the release guard: `node scripts/check-packables.mjs` — must pass; fails on `0.0.0` or empty `extensions/`.

### Live integration suite

`tests/live.test.ts` is the guard against the class of bug that motivated it: every other test only
replays a fixture through `parseLine`/`extractResult`, which can never catch a `buildArgs` the real
CLI now rejects outright — exactly what happened twice before this suite existed (`codex exec
--ask-for-approval`/`--thread-id`, `opencode run --permission`/`--add-dir`, see the Gotchas entry
below). It spawns each *detected* harness's binary for real, once, with a tiny read-only prompt in a
scratch git repo, and asserts the basics a fixture can't: the process actually runs, a real result
comes back, `sessionId` is populated, and the metrics that harness is known to genuinely report
(per `docs/acp-harness-assessment.md`'s comparison table) are present.

Opt-in only — `PI_DELEGATE_LIVE=1 bun test tests/live.test.ts` (needs real installed binaries, real
auth, and for most harnesses real API spend). Always name `tests/live.test.ts`: an unfiltered live run is
still pinned (see the `PI_CODING_AGENT_DIR` bullet) but runs, and pays for, everything. Never runs in CI or plain `bun run verify`; without the
env var it registers one test that logs how to run it and otherwise does nothing. A harness whose
binary isn't on `PATH` is skipped (logged, not failed) via each harness's own `detect()`. Use
`--timeout <ms>` (bun's own per-test timeout, default 5000ms) generously — e.g. `--timeout 90000` —
since it's independent of the `timeoutMs` passed into `runHarness`/`runAcpHarness`; a mismatch there
doesn't just fail cleanly, it lets an abandoned child process's late `close` event fire after bun has
already moved on to the next test and get misattributed to whatever test happens to be running then.

A harness's own account state is a legitimate, real reason for this suite to fail, not a suite bug —
e.g. this session's `omp`/`opencode` account had exhausted its default free-tier model's monthly
quota (`docs/acp-harness-assessment.md` §2's omp findings — confirmed here to extend to opencode's
stdout default model too, since both share the same `opencode-go` credential), so `live: amp` and
`live: opencode` failed for account reasons, not code ones, the one time this session ran it for real
(claude/codex/devin passed). Don't special-case such failures into skips — a heuristic on error text
is more likely to mask a real regression than correctly identify a billing one; an honest failure with
the real error message is the correct signal.

## Gotchas (each cost real time — don't rediscover them)

- Unscoped `pi-harness-delegate` — no `--access public` dance for scoped name; but keep `files: ["extensions","templates"]` so subdirs ship.
- `stream-json` requires `--verbose` for claude (do not drop).
- `--no-session-persistence` keeps claude runs from littering session files; other harnesses use their own session flags.
- Peer deps `"*"` (`pi-ai`, `pi-coding-agent`, `pi-tui`, `typebox`) — pi bundles them; never add to `dependencies`.
- Harness CLIs change args often — version-gate `detect()` and snapshot one real JSONL transcript before locking parser. Confirmed the hard way: as of codex-cli 0.149.1 and opencode 1.18.16, the flags this repo previously assumed (`codex exec --ask-for-approval`, `codex exec --thread-id`, `opencode run --permission`, `opencode run --add-dir`) are all rejected outright by those CLIs — every codex/opencode delegation would fail before emitting a single JSONL line. Re-verify flags against `<binary> <subcommand> --help` whenever bumping a pinned harness version, not just the JSONL schema.
- `amp`/`omp` isn't one CLI with two names — `omp` ("Oh My Pi") has a completely different flag surface from the real Sourcegraph Amp CLI it's aliased to. Its `resolveAmpBinary()` PATH probe (in `amp.ts`) only picks whichever binary is actually present; it doesn't validate that binary's schema matches what's wired.
- `opencode run` does not exit cleanly after its default model's stream errors out (confirmed live via `--print-logs --log-level DEBUG`: an `AI_RetryError` after 3 retry attempts is logged, then the process just hangs with no further output and no exit) — it relies entirely on the caller's own `timeoutMs` to bound it, same as a genuine hang would. Don't read a `runHarness` timeout against `opencode` as proof of a bug in this repo's code without checking `--print-logs` first; it may be `opencode` itself failing to exit on its own error.
- **Bun for dev, npm for publish.** CI/release use `bun install`/`bun run` everywhere, but `bun run release` calls `changeset publish` which runs `npm publish --provenance` via npm (OIDC). No npm token in repo — `id-token: write` mints it. First publish of a new package must be local with 2FA (`bun run release`).
- `devin`'s interactive workspace-trust gate (`devin -p`/interactive `devin` refuse in an untrusted directory) does **not** apply to `devin acp` — confirmed live: the raw ACP `initialize`/`session/new` handshake against a directory `devin` had never seen succeeded with no refusal, in the same test where `devin -p` in that exact directory refused. Don't add a trust-check hint or a `skip_workspace_trust` bypass on the strength of the design note's `-p`-based finding without re-verifying against the actual `acp` subcommand — it's not the same gate.
- An ACP agent does not exit once `session/prompt`'s response arrives — the session can outlive one turn. `acp-runner.ts` must explicitly finish and kill the process itself the moment that response resolves; waiting on `proc.on('close')` (the stdout harnesses' pattern) hangs until the process's own timeout, because `stdin` is deliberately held open for the run.
- Every exit path in `acp-runner.ts` must `proc.kill()` — an ACP agent exits only on stdin EOF (never sent) and `fail()`/`finish()` don't kill on their own. A handshake-step rejection (bad modeId, JSON-RPC error, `HANDSHAKE_TIMEOUT_MS`) is easy to miss since it's the one path that doesn't already have a kill nearby — the `.catch` on the handshake IIFE needs its own explicit `proc.kill('SIGKILL')`, confirmed to leak a live `devin acp` process without it.
- `session/set_mode` is spec-optional (`Agent.setSessionMode` is `?`, `NewSessionResponse.modes` is nullable) — calling it unconditionally would fail the whole handshake with a raw "method not found" against a mode-less agent instead of a clear message. `acp-runner.ts` checks capability first (see the bullet above); a harness that can't confirm mode support is a hard error, not a silent downgrade to whatever permissiveness the agent defaults to — we already promised the caller a specific tier.
- opencode's `build` mode (where `edit`/`danger` both land over ACP) does **not** call `session/request_permission` for a write — live-verified with a real file-creation prompt (`tests/fixtures/opencode-acp-build-write.jsonl`). This was the one open question gating whether opencode ACP shipped at all (`docs/acp-harness-assessment.md` §4/§7) — closing it needed an actual write attempt under `build`, not just reasoning from the `plan`-mode block that was already captured.

## Scope notes

- Do not add a second delegation mechanism — harnesses are the extension point; templates second.
- Prefer adding a template or harness over adding core code.
- Harness CLIs may not emit `stream-json` — parsers must be tolerant (plain text fallback) and `extractResult` must synthesize from `streamedText` if no `result` line.
